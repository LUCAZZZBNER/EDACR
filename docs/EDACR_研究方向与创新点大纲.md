## 1. 这个领域究竟在做什么

### 1.1 EDA 是什么

EDA 是 Electronic Design Automation，即电子设计自动化。它用软件帮助工程师设计、验证和实现电子系统。本课题可以先聚焦数字芯片与开源数字 EDA，避免起步时同时扩展到模拟电路、PCB 和封装。

一个简化的数字芯片流程如下。实际工程会反复迭代，验证、时序分析与优化贯穿多个阶段。

```text
需求与架构
  ↓
RTL：用 Verilog/SystemVerilog 等描述电路行为
  ↓
验证：仿真、断言、形式化检查
  ↓
逻辑综合：把 RTL 变成门级网表
  ↓
物理实现：区域规划、布局、时钟树、布线
  ↓
检查功能、时序、功耗、面积及物理规则
  ↓
输出版图数据，供后续制造流程使用
```

OpenROAD 官方资料展示了开源 RTL 到 GDSII 流程及物理实现组件，Yosys 是开源综合工具。它们帮助你建立“芯片设计流程”和“实现这些流程的软件”之间的联系。[OpenROAD 文档](https://openroad.readthedocs.io/en/latest/)、[Yosys 官方仓库](https://github.com/YosysHQ/yosys)

### 1.2 交叉领域的分工

| 领域                   | 主要做什么                           | 在你的课题里的作用       |
| ---------------------- | ------------------------------------ | ------------------------ |
| EDA                    | 描述电路、分析约束、生成或优化实现   | 提供专业代码与正确性要求 |
| Code Review            | 检查别人提交的变更，发现缺陷和改进点 | 定义模型需要完成的任务   |
| LLM for Code           | 理解代码与自然语言，生成解释或建议   | 作为被评测的审查者       |
| 仓库挖掘               | 从 PR、评论和历史提取研究数据        | 获取真实任务与审查证据   |
| Benchmark / Evaluation | 定义输入、标签、评分与复现实验       | 形成可比较方法的测量工具 |

**可以把课题定位为“EDA 场景下的软件工程与大模型评测交叉研究”。**它需要领域知识，也需要数据构建与科学测量能力。

### 1.3 为什么代码审查值得研究

PR 可能同时修改实现、接口、测试和脚本。审查者要理解变更意图、依赖关系和异常条件。编译成功或一次测试通过只提供部分证据。

例如，工具内部把延迟单位理解错了，程序正常运行但给出错误时序判断；RTL 在正常交易下通过测试，却在下游阻塞时丢数据。审查需要解释这些问题的触发条件和后果。

已有工作已经研究真实 PR、人工审查评论、上下文增强和测试证据，你的贡献需要落到 EDA 中仍未解决的具体问题。[SWE-PRBench](https://arxiv.org/abs/2603.26130)、[ContextCRBench](https://arxiv.org/abs/2511.07017)、[c-CRAB](https://arxiv.org/abs/2603.23448)

## 2. 先分清：你要审查哪种“EDA 代码”

PPT 只写了 EDA Code Review，没有指定仓库或语言。这是最早需要确定的研究边界。

### 2.1 三类对象

| 类型                  | 代码在做什么                             | 示例问题                                             | 知识重点                                |
| --------------------- | ---------------------------------------- | ---------------------------------------------------- | --------------------------------------- |
| A：EDA 工具源代码     | 实现综合、仿真、时序分析、布局布线等算法 | 图遍历遗漏、无效对象访问、单位转换错误、网表处理错误 | C++/Python、图算法、所选工具的 EDA 概念 |
| B：硬件设计与验证代码 | 描述电路、测试平台、断言、硬件生成器     | 位宽错误、握手错误、复位遗漏、FSM 错误、测试假通过   | 数字逻辑、RTL、仿真、协议和断言         |
| C：流程与配置代码     | 组织工具、文件、约束和构建步骤           | 约束遗漏、参数不一致、配置失效、复现失败             | Tcl/Python/Shell、构建、输入输出格式    |

同一仓库可以同时包含这三类。例如仿真器实现属于 A，用它运行的 RTL 测试属于 B，调用工具的脚本属于 C。**分类要落实到具体 PR 和问题，不能只靠仓库名称。**

下表仅表示调查入口，尚未验证各仓库有足够的高质量人工审查样本。

| 项目      | 调查用途               | 官方入口                                                |
| --------- | ---------------------- | ------------------------------------------------------- |
| OpenROAD  | 物理实现工具与相关流程 | [仓库](https://github.com/The-OpenROAD-Project/OpenROAD) |
| OpenSTA   | 静态时序分析工具       | [仓库](https://github.com/The-OpenROAD-Project/OpenSTA)  |
| Yosys     | 综合、网表变换与优化   | [仓库](https://github.com/YosysHQ/yosys)                 |
| Verilator | 仿真器实现和回归测试   | [文档](https://verilator.org/guide/latest/)              |
| OpenTitan | 硬件设计与验证         | [仓库](https://github.com/lowRISC/opentitan)             |
| Chisel    | 硬件描述语言与生成器   | [仓库](https://github.com/chipsalliance/chisel)          |

**研究建议：第一版选一种主对象、2—3 个候选仓库。**先抽样检查评论质量、历史恢复能力和你能否解释问题，再确定范围。若导师指 EDA 工具研发，优先 A；若指 RTL 工程，优先 B。C 可作为辅助类别单独报告。

## 3. PPT 的思路逐项解释

### 3.1 第 1 页：PR-level EDA Code Review Benchmark

**PPT 已明确：评测单位是 PR。**PR 即 Pull Request，是请求将一组代码变更合入目标分支。一个 PR 可包含多次提交和多轮修改。

| 粒度               | 常见输入             | 能研究什么             | 容易遗漏什么             |
| ------------------ | -------------------- | ---------------------- | ------------------------ |
| 单行               | 一行及附近代码       | 局部问题定位           | 调用关系和意图           |
| Hunk               | 一个连续变更片段     | 局部评论生成           | 跨片段、跨文件影响       |
| Commit             | 一次提交             | 一次修改的整体影响     | 一个 PR 中分散的相关提交 |
| PR 的某个 revision | 某时点的完整累积变更 | 一次实际审查的整体任务 | 仍需显式提供仓库上下文   |

PR 级输入并不自动等于完整仓库。还要规定是否提供未修改代码、测试、依赖和文档，以及能否调用工具。

### 3.2 第 2 页：四步流程

**步骤 1：完整抓取 PR 的版本与评论。**包括 metadata、commits、files、commit history、diff、inline comments 和 review threads。普通讨论评论与代码行上的 review comment 是不同对象，应分别保存。[GitHub review comments API](https://docs.github.com/en/rest/pulls/comments)

**步骤 2：每个 PR 只选一个主要审查 revision。**按每条 inline comment 对应的 target revision 分组，选评论数量最多的 revision；记录 base 到 target 的 changed LOC、changed files、diff hunks。

**步骤 3：构建 Selected Revision。**用 base commit 到 target revision 的完整变更作为待审查输入，而非只截取评论附近代码。

**步骤 4：构建 Reference Comments。**用 target revision 上的实质性 inline comments 作为参考评论。

输出是 **Revision-aligned PR review instance：代码版本与参考意见对齐的 PR 实例。**

### 3.3 一个虚构例子

以下为流程示意，不是真实数据：

```text
PR #42，base = B
R1：3 条 inline comments
R2：9 条 inline comments，其中 5 条属于实质性问题
R3：1 条 inline comment，随后合并

按 PPT 规则选 R2
模型输入：diff(B, R2) + 允许的 R2 上下文
参考问题：R2 上的实质性评论，经核查与去重后整理
```

若用最终 R3 搭配 R2 评论，缺陷可能已修复，模型会被错误扣分。把 R3 代码提前提供给审查 R2 的模型，也可能泄露修复线索。

### 3.4 PPT 尚未定义的关键部分

| 未定义项         | 需要形成的决定                       |
| ---------------- | ------------------------------------ |
| EDA 范围         | 主要对象、仓库和语言                 |
| revision 与 base | 如何恢复当时代码及正确比较起点       |
| 实质性评论       | 缺陷、风险、改进、风格和讨论怎么区分 |
| 问题去重         | 同一问题的多个评论及回复如何合并     |
| 输出任务         | 发现、定位、解释、建议，是否额外修复 |
| 评分             | 语义匹配、人工审计、执行证据怎样结合 |
| 划分             | 防止同 PR、重复补丁和未来资料泄漏    |

## 4. 研究任务如何定义

### 4.1 推荐的第一版任务

**输入：**冻结的 PR 描述、base/target SHA、累积 diff，以及实验组允许访问的历史代码上下文。

**输出：**0 到 K 条有依据的发现，每条包含位置、问题机制、触发条件、影响、证据和建议。模型可以输出“没有发现足够有依据的问题”。

**评估：**发现多少已知问题、多少额外有效问题、多少无效报告，以及成本和时间。

建议输出结构：

```json
{
  "findings": [
    {
      "path": "src/example.cc",
      "side": "RIGHT",
      "start_line": 100,
      "end_line": 105,
      "category": "domain_semantics",
      "severity": "major",
      "trigger": "特定输入或配置",
      "claim": "问题机制",
      "impact": "后果",
      "evidence": ["历史代码位置或工具输出"],
      "suggestion": "针对性建议"
    }
  ]
}
```

依赖文件或未修改行也可能是有效报告位置。定位规则应事先定义。

### 4.2 可以拆分的能力

1. 问题发现：识别根因和触发条件。
2. 定位：找到相关文件和范围。
3. 解释：说明后果，提供可核查证据。
4. 建议：给出适用于当前约束的改进。
5. 工具使用：借助构建、测试、仿真或分析减少误报。

生成补丁并通过测试属于额外任务，应单独定义指标，避免将修复能力直接等同于审查能力。

## 5. 为什么 EDA 审查难

### 5.1 工具源代码

| 类型         | 示意机制                                | 难点                   |
| ------------ | --------------------------------------- | ---------------------- |
| 单位与尺度   | ps/ns、数据库长度单位、网格坐标换算错误 | 数值合法但物理意义错误 |
| 电路图语义   | 漏连线、错误处理多驱动或常量节点        | 要理解网表和工具语义   |
| 约束传播     | 路径筛选变化导致约束误用                | 要理解约束范围         |
| 优化有效性   | 变换破坏等价性或产生回退                | 要有功能或性能证据     |
| 不变量与缓存 | 更新连接后未同步索引或缓存              | 根因和症状可能跨文件   |
| 通用软件缺陷 | 空指针、越界、溢出、资源管理            | 应与领域缺陷分开统计   |

### 5.2 RTL 与验证代码

| 概念           | 必须理解什么                  | 常见风险                 |
| -------------- | ----------------------------- | ------------------------ |
| 组合与时序逻辑 | 电路并行运行，状态随时钟变化  | 不完整赋值、时序关系错误 |
| 位宽与符号     | 截断、扩展、有符号/无符号运算 | 边界输入错误             |
| 复位           | 初始化与解除条件              | 控制状态未恢复           |
| FSM            | 状态、转移、输出和异常策略    | 死锁、错误转移           |
| 握手与背压     | valid/ready 等接口约定        | 阻塞时数据变化或丢失     |
| CDC            | 跨时钟域信息传递              | 控制信号未同步           |
| 验证完整性     | 测试的观测点与覆盖范围        | 错误测试导致假通过       |

例如在常见 ready/valid 协议下，下游未接收时数据保持行为要遵守接口规范。不能仅因为变量叫 `valid` 就判定有协议错误。

Phoenix-bench 已研究仓库级硬件维护，并报告跨层级信号推理等困难。它是硬件工程参照，但目标与 PR 审查发现不同。[Phoenix-bench](https://arxiv.org/abs/2605.15226)

### 5.3 流程代码

配置缺陷可能只在某个工艺库、设计规模或工具版本下出现。审查需要明确输入格式、约束、单位、版本、运行阶段和随机种子。PPA 即功耗、性能、面积，比较结果时要固定设计与环境。

## 6. 前置知识：学到什么程度能开始

### 6.1 通用基础

| 知识            | 最低可用水平                               | 自测任务                     |
| --------------- | ------------------------------------------ | ---------------------------- |
| Python          | 文件、JSON/JSONL、HTTP、异常、简单数据分析 | 统计 PR、评论和排除原因      |
| Git             | commit、branch、diff、merge-base、历史恢复 | 在两个 SHA 间生成并解释 diff |
| GitHub 数据模型 | PR、review、comment、thread                | 解释不同评论为何不能混成标签 |
| 软件工程        | 单元/回归测试、构建、日志、依赖            | 在历史版本复现一个问题       |
| 基本统计        | precision/recall、抽样、置信区间           | 解释平均分如何掩盖误报       |
| 实验方法        | baseline、控制变量、ablation、划分         | 写出可证伪假设及对照组       |

### 6.2 按研究对象补 EDA 知识

**共同基础：**门、触发器、时钟、状态机、模块和连线，RTL/网表/版图的区别，综合与仿真的区别，时序约束的含义。

**A 类优先：**C++ 对象生命周期、容器与接口，构建系统，图算法，所选工具的核心数据表示和一个子模块。研究 STA 就补时序路径，研究物理实现就补布局布线与几何表示，研究综合就补网表变换。

**B 类优先：**Verilog/SystemVerilog、非阻塞赋值、位宽与符号、测试平台、波形、握手协议和基本断言。复杂 CDC、UVM 和形式化验证可以按样本需要深入。

**C 类优先：**Tcl/Python/Shell、构建依赖、路径、工具参数、配置层级与输入输出格式。

起步时掌握 LEF/DEF、Liberty、SDC、GDSII 各自用于什么即可，与样本相关时再深读。不要要求自己先精通全部 EDA。

### 6.3 大模型基础

先掌握 token 与上下文限制、提示构造、结构化输出、模型版本固定、采样随机性、检索、工具调用及 LLM-as-judge。

RAG 是检索相关代码或资料再提供给模型；agent 允许模型按需要读取文件、搜索和调用工具。裁判模型则辅助判断报告与参考问题是否对应，仍需人工校准。

**第一阶段不需要训练一个大模型。**现成模型就能完成数据构建与评测。若以后微调，再补优化、过拟合、训练验证划分、参数高效训练和计算资源规划。

### 6.4 可以暂缓的内容

完整流片流程、所有 EDA 算法、深度学习训练细节、复杂多 agent 系统都可以按需要学。优先达到“独立解释一条领域审查意见，并核查对应代码”的水平。

学习入口：[Git diff](https://git-scm.com/docs/git-diff)、[Git merge-base](https://git-scm.com/docs/git-merge-base)、[GitHub PR API](https://docs.github.com/en/rest/pulls/pulls)、[HDLBits](https://hdlbits.01xz.net/wiki/Main_Page)、[Verilator](https://verilator.org/guide/latest/)、[OpenROAD](https://openroad.readthedocs.io/en/latest/)。HDLBits 适合数字逻辑与 Verilog 练习，A 类研究不必先做完全部练习。

## 7. 数据集如何做到可信

### 7.1 核心是恢复当时的审查任务

```text
候选仓库与 PR
  → 保存原始 API 数据及抓取时间
  → 恢复 review / commit / comment 时间关系
  → 核查原始锚点与历史代码
  → 按 PPT 规则选择主要 revision
  → 构建累积 diff 和允许的上下文
  → 筛选实质性意见、合并独立问题
  → 人工核查与证据审计
  → 去重、分组划分、冻结版本
```

公开 API 不保证每个 PR 的完整历史始终可恢复。强制推送、版本删除、评论编辑等情况需要记录状态和排除原因。

### 7.2 版本对齐的六个易错点

1. **当前锚点与原始锚点不同。**保存 `commit_id`、`original_commit_id`、当前/原始行号、`diff_hunk`、所属 review 的 `commit_id` 和时间戳，不要只按当前 `commit_id` 分组。
2. **revision 要用多项证据确定。**原始锚点和 review 提供线索，还要验证文件内容、hunk 与当时状态。无法确认的实例进入不确定集合。
3. **LEFT 与 RIGHT 不同。**LEFT 是旧侧、RIGHT 是新侧。删除行的问题通常按 base 侧解释，不能全转成 target 行号。
4. **回复不等于新问题。**保存完整 thread，但消息数与独立问题数分别统计。
5. **行号可能为空或 outdated。**尝试用历史 hunk 恢复，失败就标状态，不随意补行号。
6. **base 会变化。**明确采用固定 base、当时目标分支状态还是比较祖先，核查原始 PR diff 后冻结实际 SHA。

GitHub API 展示这些锚点字段，review API 提供审查记录。以上是需要验证的数据协议，不能保证单个字段恢复所有历史。[comments API](https://docs.github.com/en/rest/pulls/comments)、[reviews API](https://docs.github.com/en/rest/pulls/reviews)

Git 两端树比较与基于 merge-base 的比较可能不同。记录命令、参数、版本和比较 SHA，不能把最终 merge commit 当作所有审查时点的 base。[Git diff](https://git-scm.com/docs/git-diff)、[Git merge-base](https://git-scm.com/docs/git-merge-base)

### 7.3 评论最多的 revision：优点与偏差

**PPT 规则：**按 inline comment 数量选最多的 revision，优点是审查材料较多。

要检查：回复多但问题少、风格争论多、少数大 PR 主导，以及零评论 PR 无法进入主集。保存原始消息数、thread 数和实质性问题数。

**研究建议：**保留 PPT 规则为主版本，另外对照“按实质性独立问题数选择”和“首个可用审查 revision”。这两种是敏感性分析，不能替换原规则后仍声称完全照搬 PPT。

相同计数应有确定性规则，例如选最早满足条件的 revision。没有可用实质性问题的 PR 不进入带参考问题的主集合，另行处理。

### 7.4 实质性评论怎样标注

| 类型                           | 处理建议                           |
| ------------------------------ | ---------------------------------- |
| 明确功能缺陷或条件下的错误行为 | 纳入 defect 主任务，要求证据       |
| EDA 语义、约束、单位、协议风险 | 纳入 domain 类，说明假设           |
| 性能/PPA 回退                  | 有可比较证据时纳入对应子任务       |
| 测试不足、维护性、设计建议     | 放入独立 improvement 类            |
| 格式、命名与个人偏好           | 排除主缺陷指标或单列               |
| 问句、讨论、赞扬               | 结合 thread 判断，不机械按句式筛选 |
| 回复、重复、机器人评论         | 保存元数据，通常不算独立人工问题   |

“实质性”不等于“确认缺陷”。建议区分两个维度：

```text
intent：defect / risk / improvement / question / style
证据状态：confirmed / supported / uncertain / refuted
```

后续修复能加强证据，但“作者采纳”“PR 合并”“thread resolved”都不能单独证明意见正确。也不要只按字数筛选。

### 7.5 原始评论不是完备真值

人工可能漏报，也可能评论错误。未匹配参考评论的模型报告有三种可能：误报、额外有效发现、证据不足。

建议建立两层：

1. **全量可追溯参考集：**测核查后的已知问题召回，不宣称覆盖全部缺陷。
2. **深审计子集：**专家进一步审核报告，补充有效问题，评估精确率、额外发现和误报。更新标签应有版本，冻结后重评全部方法。

DeepCRCEval 已讨论参考评论质量与文本相似度评价的局限。你的工作需要把领域标签和实际证据落实到 EDA。[DeepCRCEval](https://arxiv.org/abs/2412.18291)

### 7.6 信息泄漏与数据划分

模型输入只能包含审查时可获取的信息。参考评论、后续修复与解释、未来文档和新增测试属于标签侧或隐藏评测侧。

要检查 PR 描述/issue 是否事后编辑加入答案，检索索引是否来自最终分支，agent 是否能访问评论和未来提交。仅保存代码 SHA 不能消除文本时间泄漏。

同一 PR 的全部 revision 同组，cherry-pick 与近重复补丁去重或同组。分别报告时间划分与跨仓库划分，它们检验不同泛化能力。公开代码可能进入模型训练，时间划分只能降低部分风险，不能证明无污染。

只采“有人工评论且成功合并”的 PR，会偏向有问题、有修复证据的变更。若研究真实误报负担，要增加单独深审计的控制集合；零评论不等于无缺陷。

### 7.7 建议数据结构

```text
身份：instance_id、repo、pr_number、source_url、collection_time
版本：base_sha、target_sha、review_cutoff_time、revision_selection_rule
对齐：review_id、原始/当前锚点、alignment_status、alignment_evidence
输入：diff、historical_pr_text、context_manifest、context_hash
规模：added_LOC、deleted_LOC、changed_files、diff_hunks
标签：issue_id、category、severity、trigger、impact、evidence_status
关系：issue 对应 comment_ids / thread_ids、人工标注记录
隐藏证据：后续修复、测试、日志、专家核查
复现：工具版本、环境、命令、split、内容哈希
```

changed LOC 可定义为新增加删除行数，但要冻结定义。重命名、二进制、生成文件、子模块、空白变化及缺失 patch 均需明确规则，不能把缺失值当零。

## 8. 如何评测：发现问题的质量

### 8.1 问题匹配

先把人工评论与模型重复报告各自合并为独立问题，再比较根因、触发条件和影响。一对一匹配，每个问题最多计一次。

同一文件或关键词相似不保证正确，表达不同或定位略偏也不自动错误。LLM 裁判使用固定 rubric、盲化方法名称，在人工审计样本上校准。

### 8.2 指标与分母

令 `G` 为核查后的已知问题集合，`P` 为去重后的报告，`M` 为一对一匹配：

```text
已知问题召回 = |M| / |G|
有效报告精确率 = 确认有效的模型报告数 / 已审核的模型报告总数
误报负担 = 确认无效的报告数 / 已审核 PR 数
额外有效发现率 = 有效且未匹配 G 的报告数 / 已审核 PR 数
```

如果只审核抽样报告，必须用抽样设计估计精确率，不能将抽样分子除以全部输出。未知报告单列，也可展示未知均有效/均无效的上下界。

**缺少完备标签时，不能将所有未匹配报告记为 FP。**真实负例总量往往难定义，因此慎用 `FPR = FP/(FP+TN)`，优先报告每 PR 无效报告数。

完整审计子集上可用统一扩充真值计算 precision、recall、F1。全量已知问题召回与抽样精确率的分母不同，应分别解释，避免组合成貌似标准的 F1。

`|G|=0` 时召回不定义，单列误报；没有输出而存在问题时召回为零，精确率不定义。

### 8.3 主报告表

| 指标                        | 回答的问题                 |
| --------------------------- | -------------------------- |
| 已知问题召回，micro/macro   | 找到多少，是否被大 PR 主导 |
| 审计集有效报告精确率        | 报告有多可信               |
| 无效报告数 / PR             | 人类需要处理多少噪声       |
| 类别和严重度分层            | 是否发现 EDA 关键问题      |
| 定位与解释质量              | 是否可核查、可采取行动     |
| 额外有效发现                | 是否补足人工遗漏           |
| 成本、延迟、token、工具次数 | 收益的代价                 |
| 预算下的质量曲线            | 同等审核负担下谁更有效     |

严重程度用明确定义和上下文判定，模型自报 severity 不能直接视为真值。若使用加权分数，权重在开发阶段冻结，同时报告未加权结果。

### 8.4 BLEU / ROUGE 不宜作主指标

文本相似度不能可靠证明问题发现正确：复述可能很像，正确意见也可能完全换一种表达。可作为历史比较辅助，主评价使用问题语义、证据与有效性。[DeepCRCEval](https://arxiv.org/abs/2412.18291)

### 8.5 人工校准与统计

先双人独立标注一部分样本，讨论分歧、修订 rubric，再扩展。报告一致性、分歧类型和裁决方式。

以 PR 为主要实验单位，做配对比较与 bootstrap 置信区间；展示逐仓库结果，样本充分时考虑仓库聚类。固定采样配置，按资源重复关键实验，避免把一次小分差当稳定结论。

## 9. Baseline 与实验矩阵

### 9.1 推荐层次

| 组别 | 允许输入或能力                 | 检验目的             |
| ---- | ------------------------------ | -------------------- |
| B0   | 空输出                         | 召回下界与误报对照   |
| B1   | 通用 LLM + diff + 冻结 PR 描述 | 简单可复现审查能力   |
| B2   | B1 + 邻近函数/模块             | 局部上下文价值       |
| B3   | B1 + 等预算检索的依赖/规范     | 针对性上下文的价值   |
| B4   | B3 + 构建、测试或仿真工具      | 工具证据是否降低误报 |
| B5   | 你的领域专门方法               | 所提方法的实际增益   |

另外加入适用的 lint、静态分析、回归检查，说明传统工具覆盖哪些问题。只在其适用范围比较，不将风格警告与领域缺陷混为同类报告。

CodeReviewer 可帮助理解早期任务建模，但与现代 PR agent 设置不同，是否正式纳入应由任务兼容性决定。[CodeReviewer](https://arxiv.org/abs/2203.09095)

### 9.2 公平性要求

冻结模型 ID、服务日期、提示、采样参数、输出上限、检索规则、工具版本、超时与失败处理。方法比较尽量使用同一模型。限定最大报告数 K，同时展示不同 K 的曲线，减少“多说就多中”的干扰。

检索在相同 token 预算下比较；agent 记录总 token、工具预算和时延。隐藏参考评论和未来修复。工具失败单独报告，不能全部算成模型语义失败。

### 9.3 不要预设上下文越多越好

SWE-PRBench 在特定设置中报告上下文扩充后的退化，ContextCRBench 报告文本上下文的帮助。两者任务和构造不同，不能直接外推到 EDA。[SWE-PRBench](https://arxiv.org/abs/2603.26130)、[ContextCRBench](https://arxiv.org/abs/2511.07017)

可测同预算下的随机邻近上下文、函数/模块上下文、领域依赖检索、规范检索。如果同时增加信息与预算，就无法分清收益来源。

## 10. 六个创新候选：问题、假设、实验与失败判据

以下均为候选研究，既不是已完成贡献，也不保证文献中没有类似方法。建议选一个主线，最多再加一个辅助方向。

### 10.1 A：版本对齐是否改变评测结论

**问题：**将评论配到最终代码、当前锚点或错误 base，会否改变问题召回和模型排序？

**假设 H1：**严格恢复审查 revision 能减少无效标签，部分测量差异来自代码与标签错配。

**实现：**定义对齐证据和人工审计规则，标记已验证、部分验证、无法恢复；报告恢复率与排除偏差。

**实验：**同一批 PR、同一模型、同一预算，比较严格对齐、最终版本配旧评论、按当前字段简单分组三种协议。错配组仅作离线诊断。控制版本间 diff 长度影响，分层展示问题已修复/仍存在的情况。

**指标：**参考问题确实存在的比例、定位有效率、召回变化、方法排序稳定性、恢复率。

**失败判据：**历史难恢复，或不同策略几乎无差异。前者缩小范围并报告偏差，后者把对齐作为质量控制，不夸大为主要新发现。

**创新边界：**已有工作关注过时评论和数据质量，价值要来自 EDA 系统审计和测量影响证据，不是单纯保存 SHA。

### 10.2 B：EDA 专业语义与跨文件推理标签

**问题：**模型漏掉的是一般软件缺陷，还是 EDA 语义与不变量？

**假设 H2：**通用模型在部分专业类别较弱，提供领域证据比添加无关代码更有效。

**实现：**分类通用缺陷、单位/约束、电路表示、算法不变量、RTL 协议/时序、验证盲区，只保留目标对象适用类别。另标证据范围：diff 内、文件内、跨文件、外部规范。

**实验：**比较通用检索与领域检索。A 类可检索对象不变量、约束链、单位定义；B 类可检索模块实例、信号传递和协议。固定模型/token，消融规范、依赖，再加入随机上下文对照。

**指标：**逐类别召回、有效报告比例、领域类别增益、证据命中率。

**失败判据：**每类样本太少，或标注分歧大。先做 30—50 个 PR 的 pilot，必要时合并类别，不用极少样本支撑普遍结论。

**创新边界：**硬件跨层级推理已有研究。聚焦审查任务的标签与检索增益，而非笼统声称首次发现硬件推理难题。[Phoenix-bench](https://arxiv.org/abs/2605.15226)

### 10.3 C：有执行证据的审查发现

**问题：**模型声称发现错误时，能否给出可运行、可归因的证据？

**假设 H3：**证据要求能提高精确率，但可能减少召回或增加成本。

**实现：**在可执行子集提供编译、测试、仿真、断言或分析证据。可见测试应符合当时信息边界，后续构造测试放在隐藏裁判侧。

**实验：**比较纯文本、允许工具、要求最小复现证据三组；冻结环境，记录环境失败和测试覆盖不足。

**指标：**证据支持的有效发现比例、无效报告/PR、召回、执行成功率和成本。

**失败判据：**环境难搭、证据无法归因、可执行子集偏向简单问题。报告选择偏差，避免把子集结论推广到全部 EDA。

**重要限制：**泛化日志错误不自动证明具体报告。根据问题性质选择 base、target 和修复版本的比较；形式化检查只覆盖建模的属性和假设。[SymbiYosys](https://github.com/YosysHQ/sby)

**创新边界：**c-CRAB 已研究测试驱动评测。新的贡献应是 EDA 环境、专业属性与证据归因，不是“用测试验证评论”本身。[c-CRAB](https://arxiv.org/abs/2603.23448)

### 10.4 D：人工标签不完备时的额外发现评价

**问题：**模型找到人工没说过的问题时，简单匹配是否会将它判为误报？

**假设 H4：**部分未匹配报告有效，审计后精确率与模型排序可能改变。

**实现：**建立盲化深审计子集，用统一审核范围或统一抽样规则，记录有效、无效、未知及证据。

**实验：**比较仅参考评论匹配与专家扩充标签后的结果，分析额外发现类别。标签冻结后重评全部方法。

**指标：**额外有效发现/PR、未知比例、精确率区间、排序稳定性、人类审核时间。

**失败判据：**专家成本过高，或大部分报告无法确认。控制输出条数与子集规模，不只审核某一个方法。

**创新边界：**人类/LLM 评价与标签质量已有工作，贡献要落在 EDA 证据协议和量化影响。

### 10.5 E：修复前后成对样本，检验“持续乱报”

**问题：**缺陷修复后，模型是否还在相同位置报告相同问题？

**假设 H5：**部分方法依赖表面线索，不能稳定区分缺陷存在和已修复。

**实现：**确认 R_before 存在某问题、R_after 已解决，优先选择其他改动少的修复对。

**实验：**盲化顺序，两个版本采用相同协议；可加控制版本，分离修复与重构的混杂。

**指标：**修复前发现率、修复后仍报告该问题的比例、成对区分能力。

**失败判据：**后版本改动过多或修复证据不足，无法归因。缩小成对子集。

**重要限制：**后版本仅保证特定问题解决，不保证整个 PR 无缺陷。主集保持 PPT 的每 PR 一个实例，成对子集单独诊断，所有版本必须在同一划分。

### 10.6 F：按人类审核负担优化审查策略

**问题：**相同人类阅读预算下，哪种方法更有用？

**假设 H6：**允许拒答、限制报告数或增加证据确认，可能减少噪声；扩大输出主要增加负担。

**实现与实验：**改变 K、证据阈值或确认步骤，绘制有效召回—无效报告/PR—成本曲线。阈值只在开发集选择。

**指标：**每条报告有效率、相同误报预算下的召回、单位成本有效发现。

**失败判据：**精确率提高只是因模型完全不报告，或收益抵不过时间成本。必须同时观察召回与成本。

**创新边界：**CR-Bench 已讨论有效发现与虚假报告权衡，新增贡献应体现 EDA 风险或具体有效策略。[CR-Bench](https://arxiv.org/abs/2603.11078)

### 10.7 如何选择主线

| 组合              | 适用情况                       | 优点                 | 主要难点           |
| ----------------- | ------------------------------ | -------------------- | ------------------ |
| A 主线 + B 诊断   | 第一次科研，先建可信 benchmark | 紧贴 PPT，问题清楚   | 版本恢复与专业标签 |
| B 主线 + 检索方法 | 想做评测及方法改进             | 可验证等预算检索收益 | 可靠领域证据       |
| C 主线 + D 审计   | 有工具环境及专家支持           | 正确性证据较强       | 环境与人力成本     |
| E 主线            | 有清楚的修复对                 | 问题聚焦、易解释     | 修复与其他改动混杂 |

**默认建议：先做 A + B 的预实验。**若对齐影响很小但领域问题确实难，再将主线转为 B。由证据决定论文重心。

| [CodeReviewer，2022](https://arxiv.org/abs/2203.09095)   | 通过预训练建模代码审查活动              | PR 累积变更、现代模型、EDA 任务  |
| [DeepCRCEval，2024 起](https://arxiv.org/abs/2412.18291) | 评论质量、文本相似度局限、人类/LLM 评价 | EDA 标签、专业证据与执行核查     |
| [ContextCRBench，2025](https://arxiv.org/abs/2511.07017) | 上下文丰富的细粒度审查                  | 领域依赖检索、版本对齐的测量影响 |
| [SWE-PRBench，2026](https://arxiv.org/abs/2603.26130)    | 真实 PR 人工审查、上下文配置、问题检测  | EDA 对象、对齐协议与专业诊断     |
| [c-CRAB，2026](https://arxiv.org/abs/2603.23448)         | 人工审查驱动的测试与 agent 评测         | EDA 工具链、属性与证据归因       |
| [CR-Bench，2026](https://arxiv.org/abs/2603.11078)       | 有效发现和虚假报告的权衡                | 领域风险、审核预算下的实用性     |
| [VerilogEval](https://github.com/NVlabs/verilog-eval)    | Verilog 生成及功能验证                  | PR 审查发现能力，而非生成成绩    |
| [Phoenix-bench，2026](https://arxiv.org/abs/2605.15226)  | 仓库级硬件维护与执行验证                | 审查意见、历史版本、问题级评价   |

LLM for EDA 综述涉及代码生成、验证调试、知识检索、优化建模等方向。你的切口是质量保证与审查评测。[Large Language Models for EDA: Future or Mirage?](https://www.cse.cuhk.edu.hk/~byu/papers/J146-TODAES2025-LLM-EDA.pdf)

**不能把“将代码换成 EDA 项目”本身视为足够创新。**需要证明它带来现有评测未覆盖的专业问题、测量挑战或方法收益。当前检索不能证明没有类似 EDA benchmark，不能支持“首个”表述。

## 12. 8 周学习与预实验路线

该计划按有基础编程能力、每周稳定投入设计。样本数量是规划目标，不是保证可采到的数量。

| 时间    | 学习重点               | 实际交付                      | 下一步依据                      |
| ------- | ---------------------- | ----------------------------- | ------------------------------- |
| 第 1 周 | Git、PR、EDA 流程      | 边界说明，手读 5 个 PR        | 能解释 base/target/comment 关系 |
| 第 2 周 | 一类对象、一个工具模块 | 2—3 仓库抽样表，10 个候选 PR | 有人工意见和可恢复代码          |
| 第 3 周 | API、历史恢复、差分    | 10—20 完整实例及排除日志     | 能核对原始锚点                  |
| 第 4 周 | 标签与人工一致性       | 30—50 PR pilot、rubric v1    | 分歧清楚，类别可解释            |
| 第 5 周 | 模型输出与评分         | diff baseline、人工审计       | 能分析漏报与误报                |
| 第 6 周 | 对照和消融             | 对齐或领域上下文实验          | 获得支持/反驳假设的证据         |
| 第 7 周 | 扩展与复现             | 资源允许时扩到约 100—300 PR  | 质量稳定、成本可控              |
| 第 8 周 | 统计与论文表达         | 结果表、案例、局限与下一步    | 贡献及边界可说明                |

若熟悉大模型，就把更多时间放在 EDA 和标注；若熟悉数字电路，就补历史恢复、裁判与统计。时间不足时，可信的 30—50 PR pilot 也能帮助判断方向。

### 12.1 第一周的具体动作

1. 确定主对象：工具源代码、RTL/验证代码或流程脚本。
2. 从一个仓库手读 5 个 PR，记录目的、审查 revision、意见与处理。
3. 对 1 个 PR 恢复历史版本，生成 diff，核对一条意见的旧/新侧位置。
4. 写一页任务协议：模型看到什么、输出什么、如何判分、哪些属于答案。
5. 学一个与样本相关的 EDA 模块，达到能解释问题的程度。

### 12.2 资源和成本

数据整理与基础 API/文本评测可以先用普通开发环境。本地模型的 GPU 需求取决于规模，工具构建与仿真资源取决于项目。API 需要记录费用和限制，本文不估计尚未选定服务的价格。

```text
调用规模 ≈ PR 数 × 方法数 × 重复次数
总资源 ≈ 模型输入/输出 + 工具运行 + 人工标注和审核
```

先测 10 个 PR 的 token、运行时长与人类审核时间，再估算扩展。领域专家参与是高价值资源，至少争取对标注规则和代表案例进行复核。

## 13. 可直接采用的研究问题与论文大纲

### 13.1 研究问题

**RQ1：**版本与人工问题对齐的真实 EDA PR 中，模型能发现哪些问题，主要漏报和误报是什么？

**RQ2：**历史对齐和参考问题核查，相比简单选择策略会如何改变结果与方法比较？

**RQ3：**相同上下文预算下，领域依赖或规范检索能否改善专业问题检测？

可选 **RQ4：**可执行子集上，工具证据是否降低误报，成本是什么？

第一篇可以只回答前三个。避免同时承担数据集、训练、复杂 agent 和全部硬件验证。

### 13.2 暂定题目

**EDACR：面向真实 EDA Pull Request 的版本对齐代码审查评测与领域错误分析**

题目随最终证据调整。没有实际执行验证，就不要把它写进贡献标题。

### 13.3 论文结构

1. **Introduction**：实际审查困难、现有评测缺口、已实现贡献。
2. **Background & Related Work**：EDA 对象、审查粒度、评论评价和硬件 benchmark。
3. **Task Definition**：信息边界、输出格式、问题与定位定义。
4. **Dataset Construction**：仓库选择、历史恢复、revision、过滤漏斗、标签和划分。
5. **Evaluation Protocol**：匹配、审计、裁判校准、执行证据与预算。
6. **Experiments**：baseline、设置、研究问题、消融、成本与统计。
7. **Analysis**：专业类别、失败机制、错配案例、额外有效发现。
8. **Threats to Validity**：标签不完备、采样偏差、污染、环境和外推边界。
9. **Conclusion & Artifacts**：实验支持的结论、数据和复现材料。

### 13.4 建议图表

- 数据漏斗：候选到最终实例的数量与排除原因。
- 版本关系案例：评论、target 和修复之间的对应关系。
- 数据分布：语言、对象、类别、规模、证据范围。
- 逐类别结果：通用与领域问题的召回和有效报告比例。
- 配对消融：对齐或上下文策略带来的变化。
- 质量与成本曲线：召回、无效报告和运行成本。

### 13.5 最终研究材料清单

目标是可复现 benchmark，而不只是一篇说明文字：任务协议、原始来源清单、版本与对齐证据、标签 rubric、数据划分、运行配置、评价代码、审计样本和失败记录。

本次仅交付研究介绍与创新规划，尚未采集 PR、实现评测或运行模型。候选项目的样本量和所有假设都需预实验确认。

## 14. 继续与调整的判据

| 观察                           | 含义                 | 下一步                        |
| ------------------------------ | -------------------- | ----------------------------- |
| 历史 SHA/锚点大量无法恢复      | 对齐路线可用范围有限 | 换窗口或仓库，报告偏差        |
| 评论多数是风格和维护建议       | defect 标签不足      | 调整范围或改做 improvement    |
| 专业问题少、通用缺陷占绝大多数 | EDA 专门价值尚未成立 | 分层分析，找专业子模块        |
| 人工很难判正确性               | 证据不足             | 补领域知识/专家，缩小确认集合 |
| 裁判常与人工冲突               | 自动评分不可靠       | 改 rubric，扩大审计           |
| 检索收益只来自额外 token       | 方法贡献不清         | 补等预算对照和随机消融        |
| 工具大量因环境失败             | 结果混入环境噪声     | 修复环境，单列未就绪实例      |
| 对齐影响不明显                 | 主假设可能不成立     | 保留协议，转向领域诊断        |

研究可以产生有证据的负结果，例如领域上下文没有帮助、自动裁判不可靠。关键是控制混杂，说明结论适用条件。

## 15. 术语与阅读顺序

### 15.1 术语速查

| 术语                       | 含义                                    |
| -------------------------- | --------------------------------------- |
| EDA                        | 电子设计自动化                          |
| PR                         | 请求合入一组变更                        |
| Commit / SHA               | 一次提交及其内容标识                    |
| Revision                   | 可恢复代码状态，此处用冻结 SHA 表示     |
| Base / Target              | 比较起点与待审查版本                    |
| Diff / Hunk                | 版本变更 / 连续变更片段                 |
| Inline Comment / Thread    | 代码上的评论 / 评论及回复讨论           |
| Reference / Ground Truth   | 参考问题 / 按协议核查的标签，仍有边界   |
| RTL / HDL                  | 寄存器传输级描述 / 硬件描述语言         |
| Netlist                    | 电路单元与连接的网表                    |
| STA / SDC                  | 静态时序分析 / 常用时序约束格式         |
| PPA                        | 功耗、性能、面积                        |
| CDC / FSM                  | 跨时钟域 / 有限状态机                   |
| Lint / Simulation / Formal | 静态规则检查 / 仿真 / 形式化方法        |
| Precision / Recall         | 报告可信比例 / 找回参考问题比例         |
| Baseline / Ablation        | 对照方法 / 去掉或替换组件的实验         |
| RAG / Agent                | 检索增强生成 / 能规划并用工具的模型系统 |

### 15.2 按用途阅读

1. **领域地图：**[LLM for EDA 综述](https://www.cse.cuhk.edu.hk/~byu/papers/J146-TODAES2025-LLM-EDA.pdf)，先看分类，定位质量保证。
2. **审查评价：**[DeepCRCEval](https://arxiv.org/abs/2412.18291)，关注标签质量和文本相似度局限。
3. **真实 PR：**[SWE-PRBench](https://arxiv.org/abs/2603.26130) 及其[数据卡](https://huggingface.co/datasets/foundry-ai/swe-prbench/blob/main/README.md)，学习协议表达，不直接照搬阈值。
4. **上下文：**[ContextCRBench](https://arxiv.org/abs/2511.07017)，理解需求与代码上下文如何改变任务。
5. **执行证据：**[c-CRAB](https://arxiv.org/abs/2603.23448)，判断哪些方法适合迁移到你的对象。
6. **误报成本：**[CR-Bench](https://arxiv.org/abs/2603.11078)，关注发现与噪声的权衡。
7. **若选择 RTL：**[VerilogEval](https://github.com/NVlabs/verilog-eval)、[Phoenix-bench](https://arxiv.org/abs/2605.15226)，区分生成、维护与审查。
8. **实施数据协议：**[PR API](https://docs.github.com/en/rest/pulls/pulls)、[comments API](https://docs.github.com/en/rest/pulls/comments)、[reviews API](https://docs.github.com/en/rest/pulls/reviews)、[Git diff](https://git-scm.com/docs/git-diff)。

读每篇先回答：评测什么、输入允许什么、标签从哪里来、如何评分、与你差在哪里、哪个结论可以复现。记录版本和访问日期，全文核查后再引用具体数字。

## 16. 与导师讨论的一页提纲

**研究对象：**从工具源代码、RTL/验证代码、流程脚本中选一种，调查 2—3 个仓库。

**任务：**给模型审查时可见的累积变更与上下文，输出带位置、条件和证据的发现，评估召回与报告有效性。

**PPT 基础：**每 PR 选评论最多的主要 revision，以 base 到 target 的完整 diff 配该版本的实质性评论。

**优先补强：**历史恢复、评论到独立问题转换、领域标签、泄漏控制、人工校准。

**首个预实验：**做 30—50 PR 的可信 pilot，比较严格/简单对齐，再比较等预算通用/领域上下文。

**候选贡献：**可追溯数据和协议、错配的测量影响、领域问题与失败分析，是否成立由实验决定。

**最早要决定的资源：**目标类型、领域专家支持、历史工具环境、人类与模型成本。
